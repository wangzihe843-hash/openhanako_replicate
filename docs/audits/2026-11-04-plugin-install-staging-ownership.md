# Plugin install staging ownership review

Base: `252c21a4fd33e5111dba91f3cd900369548ce9f5`. The private cleanup helper removes the request's `plugins/.installing-*` directory first and its `os.tmpdir()/plugin-install-*` extraction directory second, as the former ordered list did. The same helper is called on staging errors and in the outer installation `finally`. A cleanup error still propagates, masks the in-flight error when applicable, and prevents subsequent cleanup; this preserves the previous behavior rather than changing recovery policy. Promotion, backup, restoration, format checks and extension synchronization are unchanged. Commit `5461e8958` introduced the format guard and staging-failure cleanup; this change preserves both. The helper is private, and its inputs originate from the current staging call's `mkdtempSync` results (the staging path may already have been renamed into the formal target).

The `installed-plugins` rule now owns the named staging cleanup, and its protocol binds `server/routes/plugins.ts`. The unchanged expiry of `conditional-plugin-install-cleanup` applies only to removal of the OS extraction directory. The scope does not attempt to eliminate that separate exemption or change its expiry. Static matching is not a data-flow proof; runtime tests and source fingerprint mutations guard the current association.

The generated inventory retains 65 stores, 905 sites and 33 exemptions. The seven exemptions expiring 2026-11-17 now cover 95 sites (previously 96). Compared with the baseline, only three plugin-route inventory rows change: the copied destination's variable name, and the two formerly identical exempt cleanup sites becoming the separately owned staging removal and exempt extraction removal. Only the installed-plugins protocol module descriptor and that exemption's reason and pattern change; the startup receipt is byte-identical. The fingerprint payload changes from `sha256:510044d175965c5d01c6aee18e68cb524d39987b02d1bd0caee3ea016f0c541d` to `sha256:6e4986b5acd12f93f659714217cf79ed33556397ed2bb0a57c3ebdbfa086231c`. Schema source entries change for `installed-plugins` and `plugin-download-cache`; the latter already fingerprints the shared route. This is compatible with the prior upload ownership review: no stored paths, formats, epoch, or upload behavior change. Regenerating inventory, startup receipt and fingerprint produced identical SHA-256 bytes on a second run.

Real temporary-file route tests cover success; invalid archive and validation; load and extension-sync failures with restoration of an existing plugin; staging and extraction cleanup failures on both successful installation and validation failure; cleanup order and error propagation; and preservation of adjacent staging/extraction directories and the formal plugin. Ownership tests pin both sites and expiry, reject missing and overlapping ownership and unknown targets, detect removed or duplicate sites, and reject fingerprint changes to roots and call targets. Existing global inventory expectations were updated from 96 to 95; the upload test's whole non-upload-row digest was updated for the three plugin rows. The config-scope scanner negatives are split into individual cases with the same assertions and timeout.

Validation in this environment: plugin route suite, new ownership suite, persistence registry/schema/startup suites and affected ownership suites; test TypeScript and focused ESLint. Full-suite, Windows, remote CI and independent review are not represented by these local results. An initial filename-filtered Vitest invocation also discovered tests inside the untracked handoff archive; it was interrupted and those historical-copy failures are excluded from the reported results. Subsequent runs explicitly exclude that directory.
