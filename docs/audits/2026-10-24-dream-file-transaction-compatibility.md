# Dream file-application recovery compatibility

This change covers newly started Dream file applications and manual revision restores. It preserves revision schemaVersion 1 and the existing successful restore behavior. It does not solve historical daily membership or make selecting a pre_restore revision fully reversible.

## New pending journals

The existing agent-memory-owned `dream/pending-apply.json` path gains schemaVersion 2. A journal contains the operation, revision IDs, startedAt, current compiled reset token, resolved compiled-output path, beforeFiles and beforeHash. Each beforeFiles entry names a fixed memory output or a `daily/YYYY-MM-DD.md` write target and stores base64 raw bytes, or null for original absence. beforeHash is SHA-256 of JSON.stringify(beforeFiles), used for corruption detection, not authentication. The journal is self-contained: recovery does not need its referenced historical or safety revision.

Dream records Facts, Longterm and the compiled output. Restore additionally records Today, Week and only the dates the selected revision will write. No historical absence is inferred from a revision's six-entry window. No new persistent directory, archive membership, dependency, migration batch or DATA_EPOCH change is introduced.

New operations reject an unresolved pending journal. They capture raw before-images without Facts initialization, publish and read back the complete journal, then apply files. Strict Dream reads propagate errors other than ENOENT instead of using empty fallback. The regular compiler APIs retain their default read/initialization behavior; strict reads are opt-in. Strict assembly returns its written Markdown so the caller can verify the written outputs.

File application and compensation are synchronous. A pending journal always means roll back to its beforeFiles, including after a process interruption between successful writes and journal removal. Compensation restores original bytes, removes only recorded targets originally absent, then verifies every recorded target. It skips already restored files, so replay after interrupted compensation is idempotent. Failure to restore or verify retains the journal and original error cause. Journal removal is the completion boundary; a removal error triggers compensation. Empty directories and abandoned atomic-write temporary files are not part of the authoritative-file equality guarantee.

Non-regular targets and overlapping compiled-output/source paths cannot be represented by this byte-and-absence protocol and are rejected before journal publication. Output separation covers all fixed memory inputs and metadata (plus their atomic-write scratch names), and the daily, Dream transaction/state/revision, summary and reset-archive namespaces, including files outside this operation's write set. The normal memory.md output and separate custom outputs inside or outside memoryDir remain supported. Writer preflight, capture and the v2 reader use the same logical-path check; an already-current restore also rejects an invalid configured output. The check normalizes configured paths and applies platform case normalization on macOS/Windows; it does not resolve symlinks, compare inodes or implement file authorization. No permissions are changed. Concurrent processes editing a shared directory are outside the guarantee; this is not a cross-process ownership or filesystem transaction protocol. There is no new fsync/power-loss durability promise. Notifications and report persistence after file commit remain separate and can still fail after content changes; the cautious UI error text remains necessary.

## Compatibility and preserved boundaries

Historical revisions remain schemaVersion 1. Legacy journals with schemaVersion 1 or no version keep the existing revision-based recovery, including its inability to recover raw byte formatting or original file absence. The implementation does not enrich, migrate, inspect live old pending files or infer their missing before-images. A conflicting-output v2 journal produced by the earlier unshipped candidate is refused unchanged by the stricter reader; no automatic repair, rebinding or replay is attempted. The v2 persisted shape itself is unchanged. Unsupported journal versions fail without modifying active content.

Existing current-reset checks and retirement of stale/foreign-home journals remain. A v2 journal also validates its compiled-output binding before replay. Reset archive paths retain the complete inline journal bytes under their existing registration. Version-1 revision retention and explicit pre_restore creation remain; revision pruning cannot remove a v2 journal's inline recovery bytes. Busy guards, cancellation, per-agent identity, Dream auto opt-in and retired reflection behavior are unchanged.

Daily files outside the write set, daily fingerprints, Today/Facts/daily watermarks, reset marker, Facts SQLite, summaries and scoped derivations are not rewound. Successful restore still overwrites only listed historical dates, leaves other daily files active and assembles the real current directory. The returned historical sections may therefore still differ from a reread of that directory. Resolving this and successful pre_restore undo requires the separate historical-collection design; this patch does not select that design.

## Checkpoint and rollback

The agent-memory registry includes the new transaction module in protocolModules and write-site ownership. Existing checkpoint paths cover the inline journal, active outputs and revisions; capture them together. Compatible recovery must use the same bound compiled-output path and current reset identity. Do not replay an archived or copied journal into another home, or rewind reset markers to make it current.

Old readers ignore v2 beforeFiles and use the lossy revision instead. Downgrading a home with an unresolved v2 journal is unsafe and is not certified. Finish recovery with a compatible reader before any separately reviewed downgrade, retaining evidence if recovery fails. A code rollback does not restore user bytes already lost or changed. No automatic old-data recovery or historical snapshot migration is performed.

## Verification scope

The candidate's synthetic fixture covers exact raw bytes and absence after write failures, process-interruption cut points, compensation failures/retries, read and listing errors, journal verification, self-contained recovery, stale reset retirement and legacy compatibility. It also asserts that unrelated daily files and independent metadata stay unchanged. The candidate handoff records exact source identity, baseline/candidate results and original failed-run evidence; this document does not claim Windows, real-model, GUI, power-loss or shared-home concurrency acceptance.
