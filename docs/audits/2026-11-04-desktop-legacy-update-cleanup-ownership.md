# Desktop legacy update cleanup ownership review

Base: `6c6e23f13291b3ef84568ef733d1d45138c2ed33`. This is one expiry-removal task for `desktop-legacy-update-path-cleanup`. No branch, repository copy, dependency installation, commit or push is part of this change. The two pre-existing modified private documents and the untracked handoff archive are outside the work.

## Reproduced problem and scope

The original migration in `desktop/auto-updater.cjs` compared `~/.hanako-dev` and the active data directory as strings. With an active-directory alias, a legacy-directory alias, or an alias in the parent directory, both marker paths identified the same file. The existing-destination branch unlinked the active version marker before reading it, losing the version-change evidence needed to clean Electron's pending update cache. All three real temporary-directory cases failed against the unchanged baseline; the same-path control passed. `git blame` attributes this migration to `72727ed566` (2026-03-29), preceding the plugin staging repair. This is an existing bug, not a regression from `6c6e23f1`. The default fork policy disables online updates before cleanup is reached.

The migration now compares the native canonical directory paths using the existing `canonicalizeDesktopHome` helper, explicitly passing the filesystem implementation. It performs no case folding. Existing ancestors of missing paths are resolved by that helper; inaccessible, looping, dangling or non-directory identities do not authorize source cleanup. The helper itself is unchanged.

For distinct directories, only a regular single-link legacy marker is eligible. A strict `lstat` destination probe distinguishes absence from other failures. A special or multiply linked destination stops this cleanup invocation, retaining both paths and avoiding the later write through that destination. This is an intentional fail-safe change to the ambiguous-file case. A special legacy marker is left in place. These checks bound the legacy migration; they do not redesign the ordinary active-marker reader/writer in cases where no eligible distinct legacy source exists.

For ordinary files, missing destination still means `mkdir` then `rename`; existing destination still means `unlink` of the legacy marker. Only a successful rename/unlink is followed by nonrecursive `rmdir` of the exact legacy directory. Nonempty directories and unrelated files remain intact. Migration errors retain the previous outer catch, and an unsuccessful `rmdir` is still swallowed independently. `EXDEV` has no copy/delete fallback. The current shell version, version-change and size-based cache checks, pending-cache deletion, installer/feed behavior and startup gates are otherwise unchanged. This remains a path-based legacy migration, not a transaction protecting against concurrent adversarial directory replacement.

## Electron startup incident: read-only diagnosis, no retry

The full-suite command above also ran the existing native renderer integration tests, which had not been identified before starting the full run. `tests/server-connection-csp.test.ts` has three parameter cases (`plain`, `RUNNER~1`, `escaped %25 # 空间`), each executing the installed `node_modules/electron/dist/Electron.app/Contents/MacOS/Electron` with `tests/fixtures/server-connection-csp-electron.cjs` and its isolated temporary output directory. `tests/mermaid-style-isolation.test.ts` executes the same Electron binary once with `tests/fixtures/mermaid-style-isolation-electron.cjs` and its temporary output directory. Neither suite nor fixture is modified by this patch. These are four launch attempts within one full run, with no explicit retry of either suite.

The full-run errors record Electron's exit code as null, signal `SIGABRT`, and empty stdout/stderr. Four readable macOS crash reports, `~/Library/Logs/DiagnosticReports/Electron-2026-11-04-153325{,.000,.0002,.0003}.ips`, confirm four different Electron PIDs (74733, 74738, 74747 and 76306), launched at 15:33:12–15:33:18 +0800. All reports show `EXC_CRASH` / `SIGABRT`, termination namespace `SIGNAL`, code 6 (`Abort trap: 6`), and `abort() called`, with the main-thread stack entering `_RegisterApplication`, `GetCurrentProcess` and AppKit menu-bar initialization. No fixture renderer result was produced. This points to macOS application-registration/startup in this execution environment, before renderer validation; the reports do not independently prove a particular sandbox denial or that elevated execution would cure it. It is separate from the explicit loopback `listen EPERM` failures.

After the user reported repeated Electron crash dialogs, all test launching stopped. The final related run had already completed successfully; no Electron or network test was rerun after that report, no sandbox bypass was attempted, and no elevation was requested. The cleanup implementation and its VM/filesystem/ownership verification do not require elevation. Native GUI validation should stay pending for a supported independent environment/CI; any proposed one-time local elevated run would need a separate explicit decision and is not necessary to deliver this uncommitted task.

## Subsequent independent acceptance

An independent review later verified the same base, `6c6e23f13291b3ef84568ef733d1d45138c2ed33`, and the unchanged SHA-256 values of all 12 candidate files before and after its review. Against the unchanged baseline it independently reproduced loss of version-change evidence and the resulting failure to clean the pending cache for all three aliases: active directory, legacy directory, and parent directory. The same-path control passed. The candidate passed those three cases and the control, as well as the reviewed hardlink and probe-error cases.

Using existing dependencies, the independent focused run passed 341 tests across 19 files; a separate restore run passed 16 tests, with two same-home live-server network cases explicitly filtered. These runs excluded the handoff archive. The independent review did not run the full suite or launch Electron. The earlier full-suite failure counts and the diagnostic limits recorded above remain part of the evidence; these focused passes do not establish a full-suite pass or explain every failure.

After the earlier stop recorded above, one separately authorized elevated verification ran three selected tests in two files: both previously failing file-history-watcher tests and the higher-epoch override test passed. Fifteen other tests were filtered by name. The watcher captured the expected file and `.gitignore` events without watch errors; the higher-epoch server emitted its expected downgrade warning and was terminated by the test. This supports an execution-environment explanation for these three earlier failures, without establishing a single cause for all full-suite failures.

The independent review also confirmed the intentional scope of the special-destination guard: when an eligible distinct legacy source exists and the active marker is special or multiply linked, it returns from the entire `cleanUpdateCache` invocation, skipping the active-marker write and pending-cache size/version cleanup. It does not redesign active-marker handling when no eligible legacy source exists. The review ran on macOS; Windows junction behavior was not exercised, and Windows CI is still required. No cross-platform or full-suite success is claimed by this acceptance.
