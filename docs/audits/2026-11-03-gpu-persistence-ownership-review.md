# GPU startup persistence ownership review

Reviewed 2026-11-03 UTC against parent commit `4030d45b4812127e4ea86057165e68ca28bd35c5`. Classification: **compatible**. This change records existing behavior; it does not change the runtime code, on-disk format, startup phase, data epoch, restore policy, or home safety allowlist.

`desktop/src/shared/gpu-startup-policy.cjs` defines the file-local `writeJson` helper. Its only reference other than its declaration is the direct call in `writeState`, which supplies `getGpuStartupStatePath(hanakoHome)`. That path joins the home with the fixed `user/gpu-startup.json` state file. Preferences are read separately and are not a `writeJson` target. The helper creates the target's parent directory, writes a PID-suffixed temporary sibling (`${filePath}.${process.pid}.tmp`), and renames that sibling to the final file. A failed write or rename can leave the temporary sibling; this change neither cleans it up nor adds it to the final-file path pattern or unstamped-home safe paths.

The three exact physical sites (`mkdir`, `write-file`, `rename`) are now attributed to `desktop-gpu-startup-state`; the existing atomic caller rule remains. Their source file, kind, excerpt and ordinal remain the same. The complete GPU module is already covered by that store's runtime-contract source digest (`sha256:5cab554e6252fa24be8102c4a4da333a8f7b18c762d1aa4856850c2b206103da`), so a new target, helper escape or other executable change requires another review. This is a conclusion about this specific module, not a general caller-analysis guarantee.
